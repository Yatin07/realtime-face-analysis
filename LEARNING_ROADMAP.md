## What this project actually does

This is a full-stack machine learning web application with two completely separate programs running simultaneously:

1. **The Python backend** (`backend/main.py`) — a FastAPI server that receives a JPEG image, runs it through Google's MediaPipe to find and crop the face, then passes that cropped face through a custom PyTorch CNN that outputs 40 independent binary predictions (Smiling, Bald, Wearing_Glasses, etc.), and returns the results as JSON.

2. **The React frontend** (`frontend/src/pages/Home.jsx`) — a browser application with two loops running at the same time. The **fast loop** uses Google's MediaPipe loaded directly into the browser via WebAssembly to draw a green bounding box over your face on an HTML5 Canvas as fast as the hardware allows, with no network requests. The **slow loop** fires every 1.5 seconds, captures a JPEG frame from the webcam, and POSTs it to the Python backend to get the 40-attribute predictions.

The result: the bounding box tracks your face responsively while the AI data panel updates every 1.5 seconds independently.

## Phase 2 — Deep learning with PyTorch (the CNN model)

### What to learn

#### `nn.Module` — the base class for every PyTorch model

Every PyTorch neural network must inherit from `nn.Module`. This is not optional. `nn.Module` provides:
1. A parameter registry: when you define `self.fc = nn.Linear(256, 40)` inside `__init__`, PyTorch automatically finds and tracks those weights for you. Without `nn.Module`, calling `model.parameters()` would return nothing and training would be impossible.
2. The `forward()` method contract: `nn.Module` requires you to define `forward(self, x)`. When you call `model(tensor)` in inference, Python calls `forward()` automatically.
3. `.train()` and `.eval()` mode switching (see below).

```python
# backend/main.py line 27
class SimpleCNN(nn.Module):
    def __init__(self, num_classes=40, dropout=0.4):
        super().__init__()  # MUST call this — initializes nn.Module's internal bookkeeping
```

#### `conv_block` — the repeating unit of the CNN

```python
# backend/main.py lines 19-25
def conv_block(in_channels, out_channels):
    return nn.Sequential(
        nn.Conv2d(in_channels, out_channels, kernel_size=3, padding=1, bias=False),
        nn.BatchNorm2d(out_channels),
        nn.ReLU(inplace=True),
        nn.MaxPool2d(kernel_size=2, stride=2)
    )
```

These four layers are stacked in this specific order for specific reasons:

**`nn.Conv2d(in_channels, out_channels, kernel_size=3, padding=1, bias=False)`**
A convolution layer slides a 3×3 filter over the entire image and computes dot products. Each filter learns to detect one pattern (vertical edges, textures, eye shapes). `padding=1` adds a border of zeros so the output stays the same spatial size as the input. `bias=False` because BatchNorm (next layer) makes bias redundant — BatchNorm has its own learnable offset. `in_channels=3` on block1 because the input is an RGB image (3 color channels).

**`nn.BatchNorm2d(out_channels)`**
Normalizes the output of the Conv layer so the values don't grow or shrink uncontrollably between layers (a problem called internal covariate shift). During training it computes the mean and variance of each batch and normalizes. During inference (`model.eval()`) it uses the running mean/variance statistics it accumulated during training. Without BatchNorm, deep networks train extremely slowly or diverge.

**`nn.ReLU(inplace=True)`**
Replaces all negative values with zero: `f(x) = max(0, x)`. This is the activation function — without it, stacking linear layers is mathematically equivalent to one linear layer (no matter how many layers you add). `inplace=True` modifies the tensor in memory rather than creating a new one, saving RAM.

**`nn.MaxPool2d(kernel_size=2, stride=2)`**
Takes the maximum value in each 2×2 window and discards the rest. This halves the spatial dimensions (a 160×160 input becomes 80×80 after one block). Effects: (1) reduces computation for subsequent layers, (2) gives the network translation invariance — if an edge moves 1 pixel, the pool output barely changes.

**Why this exact order (Conv → BatchNorm → ReLU → MaxPool)?**
Conv produces raw feature maps → BatchNorm stabilizes the distribution → ReLU introduces non-linearity → MaxPool reduces size. ReLU must come after BatchNorm (not before) because BatchNorm works on the pre-activation values. MaxPool at the end discards the spatial info we just computed, so it goes last.

#### The four blocks and channel progression

```python
# backend/main.py lines 30-33
self.block1 = conv_block(3, 64)    # 160×160×3  → 80×80×64
self.block2 = conv_block(64, 128)  # 80×80×64   → 40×40×128
self.block3 = conv_block(128, 256) # 40×40×128  → 20×20×256
self.block4 = conv_block(256, 256) # 20×20×256  → 10×10×256
```

Each block doubles the channels (more abstract features) while halving the spatial size (less computation). By block 4, the 10×10 feature map represents abstract patterns like "there is a smiling feature here."

#### `AdaptiveAvgPool2d((1, 1))` — replacing fixed flatten

```python
# backend/main.py line 34
self.pool = nn.AdaptiveAvgPool2d((1, 1))
```

After block 4, the output is 10×10×256. To pass it to the `Linear` layer, you need to convert to a 1D vector.

**The old approach (fixed flatten):** `x.view(batch_size, -1)` assumes you always know the spatial size. If you ever change the input from 160×160 to 224×224, block 4 output is now 14×14×256 = 50176 values, but your Linear layer expects 25600. It crashes.

**Why `AdaptiveAvgPool2d((1, 1))` is better:** It averages every spatial location down to a single value per channel, regardless of the input spatial size. After this, block 4's 10×10×256 becomes 1×1×256, always, no matter what resolution went in. This is called Global Average Pooling.

After pooling: `x = x.view(x.size(0), -1)` converts from `[batch, 256, 1, 1]` to `[batch, 256]`.

#### `dropout=0.4` — regularization

```python
# backend/main.py lines 28, 35, 45
def __init__(self, num_classes=40, dropout=0.4):
    self.dropout = nn.Dropout(p=dropout)
# ...
x = self.dropout(x)
```

During **training**: for each forward pass, each neuron in the 256-element vector is randomly zeroed out with 40% probability. This forces the network to not rely on any single neuron, preventing overfitting (memorizing training data rather than generalizing).

During **inference** (`model.eval()`): Dropout is completely disabled — all 256 neurons are active, and their outputs are scaled by 0.6 (=1 - 0.4) to match the expected output magnitude. This scaling happens automatically inside PyTorch.

Why 0.4 specifically? It was tuned during the training stages. Common values are 0.2-0.5. Lower values risk overfitting; higher values risk underfitting (the network can't learn).

#### `model.eval()` — what changes between train and eval mode

```python
# backend/main.py line 85
model.eval()
```

Calling `model.eval()` flips two behaviors:
1. **Dropout**: disabled (as above)
2. **BatchNorm**: stops computing batch statistics and instead uses the running mean/variance accumulated during training

**What breaks if you forget `.eval()`:** During inference in training mode, Dropout randomly zeros neurons, so the same image produces different predictions on every call. BatchNorm in training mode uses the current batch's statistics — with batch size 1 (one image at a time in inference), the batch statistics are useless and predictions are erratic. You must call `model.eval()` before inference.

#### `torch.no_grad()` — why inference wraps in this

```python
# backend/main.py lines 182-183
with torch.no_grad():
    outputs = model(tensor)
```

During the forward pass, PyTorch normally builds a computation graph recording every operation so it can compute gradients for backpropagation during training. This graph uses significant memory and time. During inference, you will never call `.backward()`, so building the graph is pure waste. `torch.no_grad()` disables gradient tracking entirely, reducing memory usage and speeding up inference.

#### `(tensor - 0.5) / 0.5` — input normalization

```python
# backend/main.py line 175
tensor = (tensor - 0.5) / 0.5  # Normalize to [-1, 1]
```

Before normalization, pixel values are in `[0.0, 1.0]` after dividing by 255. Subtracting 0.5 centers them around 0: range becomes `[-0.5, 0.5]`. Dividing by 0.5 scales to `[-1.0, 1.0]`. The CNN's weights were learned when the training data was normalized this way. If you feed unnormalized `[0, 1]` data to a model trained on `[-1, 1]` data, the activations will be systematically wrong and predictions will be garbage.

#### `torch.sigmoid` — why not softmax for 40 attributes

```python
# backend/main.py line 186
probs = torch.sigmoid(outputs).float().cpu().numpy()[0]
```

**Softmax** is used when only one class can be true at a time (a photo is either a cat OR a dog, not both). It normalizes so all outputs sum to 1.0.

**Sigmoid** maps each logit independently to `(0.0, 1.0)` using `1 / (1 + e^(-x))`. This is used when multiple outputs can be simultaneously true — and that is exactly this problem. A face can be simultaneously `Smiling=95%`, `Male=88%`, `Wavy_Hair=72%`, `Young=60%`. These are 40 independent binary predictions. Sigmoid does not force them to compete or sum to 1.

#### `BCEWithLogitsLoss` — why binary cross entropy (training side)

This loss function was used during training (not in `main.py` inference, but documented here for completeness). Binary Cross Entropy treats each of the 40 output logits as an independent binary prediction. For each attribute, it compares the model's logit to the label (0 or 1) and penalizes confidently wrong predictions more than uncertain ones. Mathematically: `loss = -[y * log(sigmoid(x)) + (1-y) * log(1 - sigmoid(x))]`. The "WithLogits" variant combines sigmoid + BCE in one numerically stable operation — you pass raw logits from the model, not sigmoid outputs.

**Why not categorical cross-entropy (softmax-based)?** Because that forces the 40 predictions to compete. If the model is 90% sure of "Smiling," softmax would force all other attributes to sum to 10% — which is nonsensical when a person can simultaneously be Smiling AND have Wavy Hair AND wear Glasses.

## Phase 3 — CelebA dataset and training pipeline

### What to learn
- What CelebA is: a dataset of 202,599 celebrity photos, each labeled with 40 binary attributes
- What the label file looks like: a text file where each row is an image name followed by 40 values, each either `1` (attribute present) or `-1` (attribute absent)
- What multi-label classification means: each image has multiple simultaneous correct labels (unlike MNIST where each image has exactly one digit)
- What class imbalance is and why it matters for this specific dataset
- What domain shift is: training on one data distribution and deploying on another
- What data augmentation is and why it is used per-epoch

#### CelebA dataset — 200k images, 40 binary attributes

CelebA (Large-scale CelebFaces Attributes) was collected and labeled by researchers at CUHK. Each of the 202,599 images is a cropped, roughly face-centered celebrity photo. The label file `list_attr_celeba.txt` looks like:

```
202599
5_o_Clock_Shadow Arched_Eyebrows Attractive ... Young
000001.jpg -1  1  1 ... -1
000002.jpg -1 -1 -1 ...  1
```

The 40 attribute names in this project (in `backend/main.py` lines 49-59) are exactly the 40 CelebA attributes in their original order. Note they use `1` for "present" and `-1` for "absent" — but during training, these were converted to `1` and `0` before computing BCE loss.

#### Class imbalance — why some attributes are less accurate

Not all 40 attributes appear with equal frequency. For example:
- `Smiling` appears in ~48% of images → relatively balanced → model learns well
- `Bald` appears in ~2% of images → very rare → model learns a bias toward "not bald"
- `Mustache` appears in ~4% of images → rare
- `Wearing_Hat` appears in ~5% of images

When a model sees "Bald: 0" in 98% of training examples, the easiest way to minimize loss is to always predict 0. The model achieves 98% accuracy on Bald without ever learning what Bald looks like. This is class imbalance. Mitigation strategies include weighted loss (penalizing wrong predictions on rare classes more heavily) or data oversampling.

#### Domain shift — why CelebA-trained models struggle on webcam photos

CelebA images are: professional studio lighting, high resolution, front-facing, compressed by a professional, faces perfectly centered. Your webcam produces: variable room lighting, low resolution (640×480 typical), slight angles, heavy JPEG compression artifacts, background clutter. The pixel statistics of these two distributions are completely different. A filter that learned "smooth gradient across cheek = high confidence of Young" on CelebA data will encounter completely different texture patterns on webcam data. This is domain shift — training distribution ≠ deployment distribution.

The smart-cropping pipeline in `backend/main.py` (MediaPipe crop → 160×160 resize) partially mitigates this by ensuring the face is always centered and fills the frame, replicating the CelebA format more closely.

#### Data augmentation — what transforms were applied

During training (documented in `learning_notes.md` Step 13), typical transforms applied per-epoch included:
- Random horizontal flip (faces are symmetric, so flipping doesn't change attributes)
- Random crop or resize with variation
- Color jitter (slight brightness/contrast changes to simulate different lighting conditions)
- Normalization to `[-1, 1]` (matching what the inference pipeline applies in `main.py` line 175)

Augmentation artificially expands the training set. If you see the same face flipped, darkened, and slightly cropped, the model must learn features that are robust to those transformations.

#### The 4 training stages (from learning_notes.md)

The model was trained in multiple stages with increasing complexity:
- **Stage 1**: Basic CNN, high learning rate, baseline accuracy established
- **Stage 2**: Added BatchNorm to all blocks, accuracy improved (training became more stable)
- **Stage 3**: Added Dropout (0.4), reduced overfitting gap between train and validation accuracy
- **Stage 4**: Fine-tuned learning rate schedule (cosine annealing or step decay), final model saved as `best_model_gpu.pth`

The "best" model is defined by validation accuracy on a held-out set (CelebA splits into train/val/test). The `.pth` file saves only the weight tensors, not the architecture — this is why `main.py` must define the identical `SimpleCNN` class before loading.

#### `async def` in FastAPI — why it matters for concurrent requests

```python
# backend/main.py line 105
async def analyze_face(file: UploadFile = File(...)):
    image_bytes = await file.read()  # line 107
```

A synchronous web server has one thread. If it receives two requests simultaneously, it processes them one at a time — the second user waits. An async server can handle many requests concurrently because when one request is waiting for I/O (network read, disk read), Python's event loop switches to process another request. `await file.read()` tells Python: "start reading the file bytes; while you wait for the network transfer, go handle other requests." This matters in production where multiple users hit the API simultaneously.

#### Why the model loads at startup, not per request

```python
# backend/main.py lines 78-86 — TOP LEVEL, not inside the endpoint function
device = torch.device('cuda' if torch.cuda.is_available() else 'cpu')
model = SimpleCNN(num_classes=40).to(device)
model.load_state_dict(torch.load(model_path, map_location=device))
model.eval()
```

Loading a `.pth` file means reading from disk, deserializing tensor data, and allocating all the weight tensors in memory. For `SimpleCNN` this takes roughly 200-400ms. If you put this inside `analyze_face()`, every single request would spend 300ms just loading the model before doing anything. By loading once at startup (module level), the model lives in RAM permanently and inference is instant. This is standard ML API architecture.

#### CORS — why `allow_origins` was changed from `"*"` to explicit URLs

```python
# backend/main.py lines 66-75
app.add_middleware(
    CORSMiddleware,
    allow_origins=[
        "https://realtime-face-analysis.vercel.app",
        "http://localhost:5173"
    ],
    allow_credentials=True,
    allow_methods=["*"],
    allow_headers=["*"],
)
```

Browsers enforce the Same-Origin Policy: a JavaScript program from `vercel.app` is blocked from reading responses from `onrender.com` unless the server explicitly permits it. `CORSMiddleware` tells the browser "I allow these specific origins." 

Using `allow_origins=["*"]` (the wildcard) works locally and is tempting to keep, but in production with `allow_credentials=True`, the wildcard is rejected by browsers for security reasons — a malicious website could then make authenticated requests to your API on behalf of a logged-in user. Restricting to the specific Vercel URL is the correct production configuration.

#### The `/health` endpoint — why lightweight not `/analyze`


#### MediaPipe relative_bounding_box — why 0-1 fractions, why multiply by img_width

```python
# backend/main.py lines 130-137
bboxC = detection.location_data.relative_bounding_box
img_height, img_width, _ = img_np.shape

x = int(bboxC.xmin * img_width)
y = int(bboxC.ymin * img_height)
w = int(bboxC.width * img_width)
h = int(bboxC.height * img_height)
```

MediaPipe returns coordinates as fractions of the image dimensions (0.0 to 1.0) rather than absolute pixel values. This is "resolution-independent" — the same model works on a 640×480 webcam frame and a 4000×3000 phone photo without retraining. `xmin=0.3` means the left edge of the face is 30% from the left of the image. To get actual pixel coordinates you multiply by the image dimensions. `bboxC.xmin * img_width` converts the fraction to a pixel position.

#### The crop margin math — why asymmetric

```python
# backend/main.py lines 140-147
margin_x = int(w * 0.25)       # 25% on Left and Right
margin_top = int(h * 0.35)     # 35% on Top (Hair)
margin_bottom = int(h * 0.25)  # 25% on Bottom (Neck)

x_new = max(0, x - margin_x)
y_new = max(0, y - margin_top)
w_new = min(img_width - x_new, w + margin_x * 2)
h_new = min(img_height - y_new, h + margin_top + margin_bottom)
```

MediaPipe's tight bounding box starts at the eyebrows and ends at the chin. CelebA images include: hair above the eyebrows, ears at the sides, slight neck below the chin. To replicate the CelebA framing:
- **35% top**: Hair and hat extend further above the eyebrows than the face extends below the chin — hair is a much larger feature visually.
- **25% sides**: Ears, sideburns, and slight head width padding.
- **25% bottom**: Neck and chin, less critical than hair.

The margins are **asymmetric because the human head is asymmetric** — there is more hair above the eyes than chin below them.

`max(0, ...)` and `min(img_width - x_new, ...)` are safety clamps to prevent cropping outside the image boundaries (which would crash Pillow or return garbage data).

#### `base64ToFile` — why this conversion is necessary

```javascript
// Home.jsx lines 38-48
const base64ToFile = (base64String, filename) => {
    const arr = base64String.split(',');
    const mime = arr[0].match(/:(.*?);/)[1];
    const bstr = atob(arr[1]);
    let n = bstr.length;
    const u8arr = new Uint8Array(n);
    while (n--) { u8arr[n] = bstr.charCodeAt(n); }
    return new File([u8arr], filename, { type: mime });
};
```

`webcamRef.current.getScreenshot()` (from `react-webcam`) returns a base64-encoded JPEG string like `"data:image/jpeg;base64,/9j/4AAQSkZ..."`. Base64 is text — it represents binary data as printable ASCII characters.

FastAPI's `UploadFile = File(...)` expects a binary file upload via multipart/form-data, not a text string. You cannot append a base64 string to `FormData` and expect FastAPI to parse it as a file.

The conversion: `atob(arr[1])` decodes the base64 string to binary character data. The `while` loop copies it byte-by-byte into a `Uint8Array` (a typed array of raw bytes). `new File([u8arr], filename, { type: mime })` wraps those bytes in a `File` object that `FormData` can send as a proper file upload.

#### `video.videoWidth` vs `video.clientWidth` — the coordinate space bug

```javascript
// Home.jsx lines 159-160
const natW = video.videoWidth;
const natH = video.videoHeight;
```

`video.videoWidth` and `video.videoHeight`: the native resolution of the camera hardware. If your camera is 640×480, these return 640 and 480 regardless of how big the video element appears on screen.

`video.clientWidth` and `video.clientHeight`: the CSS pixel size of the `<video>` element in the browser layout. If the video element is styled `w-full` inside a 400px container, these return 400 and some height depending on aspect ratio.

**The bug this caused:** MediaPipe's `detectForVideo()` returns coordinates in the video's native pixel space (e.g., `bbox.originX=200` out of 640 native pixels = 31% from left). If you set `canvasRef.current.width = video.clientWidth` (= 400), drawing at x=200 would be at 200/400 = 50% of the canvas, which is wrong (it should be 31%). The fix: set the canvas internal resolution to `videoWidth × videoHeight`. Now drawing at x=200 is at 200/640 = 31%, matching the video's native space, and CSS scaling handles the visual stretching identically for both elements.

#### `style={{ transform: 'scaleX(-1)' }}` on Webcam only — why canvas must NOT be flipped

```javascript
// Home.jsx line 289
style={{ transform: 'scaleX(-1)' }}  // applied to <Webcam>
// Home.jsx line 294-296
<canvas
    ref={canvasRef}
    className="absolute top-0 left-0 w-full h-full pointer-events-none"
    // NO transform applied to canvas
/>
```

CSS transforms are purely visual — they flip what the user sees on screen but they do NOT affect the underlying pixel data or the coordinate system. MediaPipe reads the raw video frames (unflipped) and returns coordinates in the raw space. If the face is at raw x=100, MediaPipe says x=100. But on screen, because the video is CSS-flipped, x=100 appears visually on the RIGHT side of the screen (at screen_x = width - 100).

The canvas has the same CSS transform applied to it by being inside the same container (well, in this project, the canvas does NOT have the transform). So coordinates drawn directly at x=100 would appear at x=100 on screen — on the wrong side of the face. The fix is to manually flip the X coordinate:

```javascript
// Home.jsx line 182
const flippedX = natW - bbox.originX - bbox.width;
ctx.strokeRect(flippedX, bbox.originY, bbox.width, bbox.height);
```

If the face's raw left edge is at x=100 with width=200, the right edge is at x=300. In the mirrored world, the face's visual left edge should appear at `640 - 300 = 340` on screen. `natW - bbox.originX - bbox.width = 640 - 100 - 200 = 340`. This math inverts the X position correctly.

#### `capturePhoto` — the off-screen canvas mirror

```javascript

    const imageSrc = webcamRef.current.getScreenshot();
```

`getScreenshot()` captures the raw unmirrored frame from the camera hardware. But the user sees a mirrored video feed (CSS scaleX(-1)). #### Dynamic CDN import — why not npm install


MediaPipe Tasks Vision includes WebAssembly binaries and a `.tflite` face detection model. When installed via npm, these large binary files must be properly configured in the Vite build pipeline — but this caused Windows-specific SSL errors and file permission issues (documented in `learning_notes.md` Phase 7 Bug #1: "The NPM Cache/SSL Bug").

The solution: `await import(url)` is a JavaScript dynamic import — instead of bundling with npm, it fetches the ES module directly from the CDN at runtime. The browser downloads it, compiles the WebAssembly, and initializes the model. This runs once at page load. No npm, no build pipeline issues.

#### `delegate: "CPU"` — why GPU was avoided

```javascript
// Home.jsx line 62
delegate: "CPU"
```

MediaPipe can run on the GPU via WebGL for faster inference. But WebGL has notoriously flaky support on Windows browsers, especially with integrated graphics (Intel GPU). The failure mode is silent — the WebAssembly module crashes without a useful error message, and the entire face detection silently stops working. For a lightweight face detection model like BlazeFace (used by `blaze_face_short_range.tflite`), the CPU is more than fast enough. Choosing CPU over WebGL here prioritizes stability over theoretical speed gains.

#### `video.readyState >= 2` — why the guard is necessary

```javascript
// Home.jsx line 156
if (video.readyState >= 2 && video.currentTime !== lastVideoTime) {
```

`HTMLVideoElement.readyState` is an integer:
- `0` = HAVE_NOTHING: no information about the media
- `1` = HAVE_METADATA: duration and dimensions known
- `2` = HAVE_CURRENT_DATA: data for the current frame is available
- `3` = HAVE_FUTURE_DATA: data for next frame is available
- `4` = HAVE_ENOUGH_DATA: enough data to play without stopping

Calling `detectForVideo()` on a `<video>` that hasn't buffered its first frame (readyState < 2) throws an error because there is literally no frame data to analyze. The guard ensures detection only runs when real pixel data is available.

#### `video.currentTime !== lastVideoTime` — avoiding duplicate work

```javascript
// Home.jsx lines 150, 157
let lastVideoTime = -1;
// ...
lastVideoTime = video.currentTime;
```

`requestAnimationFrame` fires as fast as the screen refresh rate (typically 60Hz), but the camera itself typically captures at 30 frames per second. This means the animation loop runs twice for every new camera frame. Without this check, you would call `detectForVideo()` twice on the same frame, doing double the computation for no benefit. By tracking `lastVideoTime` and only running detection when the video has advanced to a new frame, you avoid redundant inference.

## Phase 9 — Real-time architecture (canvas loop + 1.5s CNN split)

### What to learn
- `requestAnimationFrame` — why it is used instead of `setInterval` for the drawing loop
- The decoupled loop architecture — why the canvas loop and backend loop are completely separate
- Memory management: `cancelAnimationFrame` and `clearInterval` in cleanup

#### `requestAnimationFrame` vs `setInterval` for the drawing loop

```javascript
// Home.jsx lines 152-191
const renderLoop = () => {
    // ... detection and drawing ...
    requestRef.current = requestAnimationFrame(renderLoop);  // line 190
};
requestRef.current = requestAnimationFrame(renderLoop);  // line 194
```

`setInterval(fn, 16)` fires roughly every 16ms (≈60 times/sec). But it fires on JavaScript's timer queue, not synchronized with the browser's painting cycle. If the browser is busy, the timer fires but the screen hasn't repainted yet — wasted computation. If the browser paints faster than 60Hz, you miss frames.

`requestAnimationFrame(fn)` tells the browser: "Call this function right before you paint the next frame." The browser guarantees the callback happens exactly once per screen refresh. When the tab is hidden/inactive, `requestAnimationFrame` automatically pauses — `setInterval` does not. This is the correct API for any animation or canvas drawing loop.

#### The decoupled loop architecture — why it works

```javascript
// Home.jsx lines 193-204 — running simultaneously and independently
requestRef.current = requestAnimationFrame(renderLoop);  // line 194: canvas loop

liveIntervalRef.current = setInterval(() => {           // line 197: backend loop
    const imageSrc = webcamRef.current.getScreenshot();
    if (imageSrc) { performLiveAnalysis(imageSrc); }
}, 1500);
```

The two loops are completely independent — they share no state except the React `results` state that `performLiveAnalysis` updates via `setResults()`. The canvas loop doesn't know or care about backend results. The backend loop doesn't know or care about what the canvas is drawing.

**Why this architecture:** If you coupled them (draw box only when backend responds), the box would update at 0.6 FPS — once per 1.5 seconds. Faces move faster than that. Decoupling gives the illusion of real-time tracking while offloading heavy computation to a background timer.

#### `requestRef` — why a ref stores the animation frame ID

```javascript
// Home.jsx line 21
const requestRef = useRef(null);
// Home.jsx line 190
requestRef.current = requestAnimationFrame(renderLoop);
// Home.jsx line 209
cancelAnimationFrame(requestRef.current);
```

`requestAnimationFrame` returns an integer ID. To cancel the loop later, you call `cancelAnimationFrame(id)` with that ID. The ID must survive re-renders of the component — if it were a regular `let` variable inside the `useEffect`, it would be lost after the effect runs. Storing it in a ref persists the ID across the component's lifecycle. This is the standard pattern for managing animation loops in React.

#### Why the `content` array must include `./src/**/*.{js,jsx}`

```javascript
// tailwind.config.js lines 3-6
content: [
    "./index.html",
    "./src/**/*.{js,ts,jsx,tsx}",
],
```

Tailwind JIT (Just-In-Time) mode scans your source files for class names and generates CSS only for the classes it finds. If `./src/**/*.jsx` is not in the `content` array, Tailwind will not scan your React components, will find zero class names, and will generate an empty CSS file. Every Tailwind class in your JSX would be silently ignored — the app would render completely unstyled.

#### Why restarting the dev server is required after editing `tailwind.config.js`

Vite loads `tailwind.config.js` at startup, passes it to PostCSS, and the configuration is cached for the entire dev session. Unlike `.jsx` files (which Vite watches and hot-reloads), the Tailwind config is part of the build toolchain configuration. If you add a new color to `theme.extend.colors`, Vite's cached config does not know about it. The new class like `bg-theme-newcolor` will not be found in any scan and will not generate CSS. A full restart forces Vite to re-read `tailwind.config.js` from disk.

```javascript
// tailwind.config.js lines 9-12
fontFamily: {
    sans: ['Inter', 'sans-serif'],    // font-sans class → Inter
```

#### Render free tier cold start — the full timeline

Render's free tier spins down Python servers after 15 minutes of no incoming requests. When a new request arrives at the sleeping server:
1. Render provisions a new container: ~15-20 seconds
2. Python starts: ~2-5 seconds
3. `import torch`: ~3-5 seconds
4. `model.load_state_dict(torch.load(...))`: ~3-8 seconds
5. `face_detector = FaceDetection(...)`: ~2-3 seconds
6. Server is ready to accept requests: total ~30-60 seconds from sleep

If the first request from the frontend hits the server before it finishes booting, the request either: (a) hangs until the server is ready (if the connection is kept alive — Render handles this), or (b) times out. The 60-second Axios timeout (`Home.jsx` lines 116, 136) gives Render enough time to wake up and process the request before the browser gives up.

The `/health` ping on page load (`Home.jsx` line 67) starts the wake-up clock early. By the time the user actually clicks "Analyze Face," the server may already be fully booted.

#### Vercel auto-deploy — how CI/CD works

Both Vercel (frontend) and Render (backend) are connected to the GitHub repository `Yatin07/realtime-face-analysis`. When you run `git push`, GitHub notifies both Vercel and Render via webhooks. Vercel pulls the latest code, runs `npm run build` (which runs `vite build` → generates `frontend/dist/`), and deploys the static files to its CDN. Render pulls the latest code and restarts the Python server with the new `main.py`. This is Continuous Integration / Continuous Deployment (CI/CD) — code changes go live automatically without manual upload steps.

#### CORS — `"*"` vs explicit origins in production

```python
# backend/main.py lines 67-71
allow_origins=[
    "https://realtime-face-analysis.vercel.app",
    "http://localhost:5173"
],
```

When `allow_credentials=True` (the setting that allows cookies and auth headers), browsers enforce that `allow_origins` cannot be `"*"`. This is a browser security rule, not a FastAPI limitation. If you try `allow_origins=["*"]` with `allow_credentials=True`, browsers will reject the CORS preflight response and block the request. Explicit origins are required in production. `http://localhost:5173` is kept for local development.

#### UptimeRobot — preventing Render sleep

An external tool like UptimeRobot (free tier) can ping `https://realtime-face-analysis-1.onrender.com/health` every 5 minutes. Since Render spins down after 15 minutes of silence, a ping every 5 minutes keeps the server permanently awake. This is why `/health` returns instantly (`{"status": "ok"}`) — it is called frequently and must be lightweight.
